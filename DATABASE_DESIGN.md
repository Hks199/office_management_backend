# MongoDB database design

This is the target schema specification with implemented phase notes. Phases 2-5 implement identity, organization, attendance/private files, customers/imports/leads and commercial histories. Phases 6-8 implement reports/history, targets/revisions/evidence/reviews, attendance calendars and dashboard export jobs. Phase 9 adds shared request_limits and production index inventory checks. Production disables automatic collection/index creation; run explicit migration commands documented in PHASE9.md.

## Conventions

Phase 9 request_limits stores a string HMAC/window/namespace `_id`, numeric hits and expiresAt with TTL=0. Atomic upserts share quotas across replicas; window identity enforces expiry even before TTL cleanup. No raw IPs are stored. Additive production indexes support employee/branch report completion ranges, employee approved milestone ranges and employee/branch effective attendance ranges. Production preflight checks all declared/prerequisite index metadata without writing business data; extra operator indexes remain untouched. See PHASE9.md for privileges, upgrade commands and limits.

Every collection has `_id: ObjectId`. Mutable entities have `createdAt,updatedAt: Date` (UTC), `revision: integer >= 0` for optimistic writes where noted. `Ref` below means an ObjectId referencing the named collection; absence is explicitly allowed only where noted. Strings are trimmed, length bounded in Joi and schemas, and never accepted as arbitrary query expressions. Nonnegative values must also be finite. Phone numbers normalize to E.164; emails lowercase under a documented company uniqueness policy. Codes use normalized uppercase unique strings. Money uses Decimal128 INR with two-decimal rounding at calculation boundaries; capacity uses Decimal128 kW. API decimals are strings to avoid binary floating-point rounding. No image binaries are stored in MongoDB.

Common indexes end with `_id` when supporting deterministic cursor pagination. `U` denotes unique. TTL cleanup is eventual, so services must check expirations themselves. Foreign keys require explicit service checks inside sensitive transactions. Mongoose schemas use strict mode, enums, required fields, immutable historical attribution, and safe response projections.

## Future AMC boundary

Separate `quotations` (versioned line items, tax assumptions, acceptance), `site_surveys`, `installation_tasks`, `amc_contracts` (projectId, contractCode, start/end dates, renewal chain, status, coverage), `service_visits` (contractId, technicianId, evidence), and `maintenance_reports`. Keep financial and contract history immutable. Renewal creates a linked contract; it does not erase the previous term. These future collections are design notes, not initial implementation scope.

## Transaction groups and validation

Employee creation verifies active role, creator policy, manager, branch and location chain; manager/branch mutations write organization revision before rechecking cycles. Attendance writes record plus audit; duplicate key maps to 409. Conversion atomically inserts the unique-source lead, customer status and event. Lead assignment/status write expected revision plus history and audit. Target revision writes definition and history. Auth refresh consumes a valid token and creates replacement in one transaction; replay revokes family. A business change must not silently succeed if its required audit event fails.

All scoped list filters wrap authorization and validated filters in `$and`. Scope is applied before aggregation. Cross-branch dedupe errors are generic. Avoid unrestricted populate; use selected fields and bounded batch lookups. Production disables automatic index creation: introduce versioned migrations, verify duplicate data beforehand, inspect `explain('executionStats')`, and monitor slow queries without raw PII. Replica-set backup/restore tests and index deployment are Phase 9 acceptance gates.

## Additional implemented identity collections

`login_attempts`: `_id` is an HMAC of normalized email and operation; count:int and expiresAt:Date with TTL. Ten login attempts or three recovery attempts per account in a 15-minute window starting at the first attempt are allowed across API instances. The HTTP/IP limiter is separate and still per process.

`security_state`: string `_id` (`bootstrap` or `administration`), revision:int. Transactional writes serialize singleton bootstrap and administrator mutations.

`credential_deliveries`: credentialId:ObjectId unique, userId:ObjectId, purpose:INVITATION/PASSWORD_RESET, encryptedToken:string select:false (AES-256-GCM), expiresAt:Date TTL, status:PENDING/PROCESSING/SENT/FAILED/EXPIRED, attempts:int, leaseUntil:Date?, leaseId:string?. Compound `(status,leaseUntil)` supports claims. Worker verifies credential eligibility before sending and removes ciphertext after success or invalidation. Job leases support retries and may deliver duplicate messages after a crash; credential redemption remains single-use.

Activity metadata is a bounded-by-caller Map<string,string>; implemented actions contain only IDs, revisions, grant strings and codes. Raw IP/customer data is not captured in Phase 2 audits. Mongoose hooks prohibit audit mutation/deletion; production DB privileges must enforce the same restriction against raw access.

## Phase 3 implemented constraints and migration

`branches`: unique branchCode; `(stateId,districtId,isActive)` lookup; partial unique branchHeadId for ObjectId values (multiple null heads allowed). Branch head is an active employee in that branch with branches:update BRANCH/ALL. Branch revision guards edits. No hard delete; deactivation requires no active employees/head. Source branch attribution in future historical collections remains immutable.

`states`, `districts`, `blocks`: unique state code, unique `(stateId,code)` district and `(districtId,code)` block. Parent/isActive/name indexes support bounded lists. Fields include code,name,isActive,revision,createdBy,sourceVersion?,timestamps; districts require stateId; blocks require districtId and BLOCK/TEHSIL kind. Parent IDs and codes cannot be reassigned through PATCH. Branch references and active children block parent deactivation.

`roles.allowsNoBranch`: boolean default false; MD/BDO seeds true. Requires sensitive delegation to change and cannot be disabled while referenced branch-less employees exist. `role_creation_policies.creatorRoleRevision` and `targetRoleRevision` store server-derived approval snapshots. User creation/reassignment rejects stale snapshots; reporting policy changes that would invalidate active edges are rejected.

`security_state.hierarchy` is the organization revision/serialization record, sharing the administration fence with role/policy writes. Employee changes use explicit expected revision. Manager/branch/role/status/contact changes invalidate affected sessions; deactivation/contact changes additionally consume outstanding credential tokens and expire queued deliveries. Pending employees receive replacement invitations on contact changes/reactivation.

Run `npm run db:indexes:organization` to create organization collections/indexes and add Phase 3 metadata. Missing role flags initialize false, with unchanged revision-zero MD/BDO templates initialized company-wide. Existing modified roles require explicit review of the company-wide flag. Missing policy revision snapshots initialize zero, preserving fail-closed behavior for roles already changed. The migration does not reassign existing users, repair invalid branches/manager chains or silently reapprove modified grants; audit/review existing Phase 2 data before using employee mutations.

Optional branch geofence/work-schedule fields in the target design remain Phase 4 extensions; Phase 3 branch DTOs cover profile/location/status/head only.

Last-administrator availability requires an active employee with completed password setup and an active role containing the core administrator grants. Pending invitations do not satisfy this safeguard.

## Implemented Phase 4 policy and correction semantics

Branch attendancePolicy contains optional same-day Kolkata startMinute/endMinute, graceMinutes, evidence age/accuracy thresholds and optional geofence. It is snapshotted at check-in. Existing rows without a policy use defaults from PHASE4.md. Corrections only change effective times and derived state; immutable activity_logs capture before/after with actor, reason and revision in the transaction. Files pin the validated S3 version. `db:indexes:attendance` creates the new unique/partial/scoped indexes explicitly without rewriting history.
## Implemented Phase 5 runtime additions

`commercial_settings`: singleton string ID customers, duplicateScope BRANCH/COMPANY, revision and timestamps. Frozen after any customer exists; queued previews snapshot and recheck policy.

`lead_exports`: createdBy, private principal/session/query/leadIds/lease metadata, status QUEUED/PROCESSING/COMPLETED/FAILED, fileId, attempts/errorCode/requestId/expiresAt/timestamps. Status/lease and creator/time indexes. Twenty-four-hour download authorization; file/version retention separate. Owner download rechecks visibility of every included lead. Export payload is capped at 5000 rows/10 MiB.

Lead runtime uses resumeStatus and nextFollowUpAt/lastContactedAt with pinned workflowVersion; contact/amount DTOs and phase-specific index/transaction behavior are in PHASE5.md. Amounts persist as Decimal128 and serialize as strings; multiplication uses BigInt hundredths and half-up INR rounding. Operational migration creates indexes/defaults without rewriting custom roles/settings/history. The separately named capability rollout only adds reviewed default receive capabilities, audits and increments role revisions; creation policies remain stale until reapproved.
