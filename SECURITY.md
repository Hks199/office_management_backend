# Security posture

## Implemented foundation and identity

Phase 9 requires MongoDB shared general/auth request quotas in production, with HMAC client keys, atomic counters, TTL cleanup and fail-closed store errors. It disables production auto-create, rejects standalone production databases, bounds pool wait, removes raw URL paths from access logs and adds live ALL-settings-protected monitoring. Container/CI tooling exercises non-root read-only execution and graceful SIGTERM; local availability/results are reported in VERIFICATION.md. See PHASE9.md for production configuration, external acceptance, restore and rollback controls.

Helmet headers/CSP; explicit exact-origin CORS; production HTTPS origins; bounded JSON parsing with compression disabled; per-IP rate limit; untrusted request-ID validation; Joi middleware rejecting unknown fields; recursive rejection of Mongo operators/dotted/prototype keys with depth limit; centralized typed errors; restricted request logging and secret redaction; no public registration; protected role/policy administration; minimal health signals; validated environment; Mongo query sanitization, bounded connection pool and no command buffering; non-root Docker runtime; readiness and graceful shutdown. Public documentation cannot be enabled in production.

Phase 2 refresh/logout require an exact allowed Origin and a session-bound CSRF header; GET /auth/csrf requires Origin to recover the token. Cookies are HttpOnly/SameSite=Strict and Secure in production. CORS is browser policy and never substitutes for authentication. Future validators must build explicit DTOs and repositories must never pass raw `req.body` or `req.query` to MongoDB. Global sanitization cannot replace route-level Joi allowlists; route params are validated after matching by feature validators. Query parser is simple and repeated/unexpected fields must fail Joi validation.

Only method/request ID/status/latency are logged automatically; paths, bodies, query strings, headers and raw errors are excluded. Driver errors and startup errors are reported generically to prevent URI credential disclosure. Use restricted operational telemetry for diagnostics, never dump the environment or raw request objects.

## Required before business deployment

Implemented Phase 2: Argon2id (64 MiB, 3 passes, parallelism 1; tune against production latency), explicit JWT algorithm/issuer/audience, 256-bit secrets from a secret manager, active-session checks, refresh rotation and family replay detection, expiring hashed reset tokens, generic account recovery, per-account/IP brute-force controls, safe invitations, secure cookies and session-bound CSRF. Derive identity from verified tokens only. Revalidate role and hierarchy on every request. Disable employee logins immediately after deactivation. Never email passwords or store long-lived browser tokens in localStorage.

Phases 3–8: authorization on every resource, scoped repository filters and aggregates, creation/delegation policy checks, protected system roles/last administrator, transactional immutable audits, safe CSV streaming and formula escaping, idempotent conversions, revision-safe lead assignments, evidence validation and scoped S3 downloads. Include IDOR tests across branch/subtree/employee boundaries and denied aggregate/export tests.

## S3 deployment policy (Phase 4)

Create a private bucket with Block Public Access, bucket-owner enforced object ownership, TLS-only bucket policy and encryption at rest (SSE-S3 or approved KMS key). Grant the runtime IAM role only object read/write on `sunvika/` and cleanup workers limited delete rights; do not grant bucket administration. No static keys in source or environment examples. A KMS deployment also needs key policy and minimal decrypt/encrypt grants.

Generate UUID object keys under `sunvika/attendance/{employeeId}/{year}/{month}/`, `sunvika/site-visits/{leadId}/{visitId}/`, `sunvika/imports/{importId}/`, or `sunvika/employees/{employeeId}/`. Resolve all IDs from authorized entities. Upload intent presigns an exact key/checksum/MIME with a strict byte-size policy where supported; confirmation checks HEAD size/type/checksum and reads bounded bytes to verify signatures. Reject HTML/SVG/executables for photograph purposes. Quarantine untrusted documents pending scanning. Attachment association rechecks owner, purpose, parent, confirmation, scan state and allowed reuse. Signed URLs are short-lived bearer capabilities and must never appear in logs or audit metadata.

Cleanup pending uploads after a recommended 24 hours using an authorized worker that deletes S3 objects before marking metadata deleted. Never drop metadata with TTL and leave sensitive objects behind. Apply approved lifecycle rules to expired evidence/documents and versioned objects; record deletions without logging contents. Upload/download/cleanup operations require live AWS integration tests in Phase 4; none are claimed in Phase 1.

## Retention recommendations requiring business approval

Use a proposed 30-day staged-import retention, 24-hour orphan-intent retention, 30-day notification retention, and 90-day security-log IP retention. Attendance photographs, employee documents, call/visit reports, customer records, and audit history need company/legal retention decisions before production; no destructive retention job is enabled. Backups inherit access controls and expiry policies. Restrict auditors to append-only data and deny application update/delete on `activity_logs`; use a separate retention administrator.

## Operational controls

Terminate TLS at a trusted ingress; restrict backend network access to that ingress before setting `TRUST_PROXY_HOPS`. Hop-count trust is unsafe if clients can take a shorter network route. Production shared quotas supplement ingress protection. MongoDB and any future Redis service must be private, authenticated and TLS-protected in production. Compose's unauthenticated local/smoke replica sets are development/test-only. Use an authenticated multi-node replica set/managed service and least-privilege DB credentials.

Run `npm run check` and `npm audit` in CI, review dependency advisories, scan container images and rotate secrets. Lockfile makes dependency resolution reproducible; image digests should be pinned by deployment tooling. Production index changes are migrations, not `autoIndex`. Alert on elevated 5xx, database disconnects, login attacks, refresh replay, import failures, audit-write failures and orphan-cleanup backlogs without retaining unnecessary PII. Security incidents revoke affected sessions, rotate compromised keys and preserve restricted audit evidence.

## Known limits

Phases 1-9 implement business APIs, shared quotas and production-readiness tooling. Live AWS/provider/ingress/backup/load and production deployment acceptance remain environment gates; general notifications remain future work. Browser GPS and photos can be spoofed. Approved business policies and external integration/security validation are required before accepting real employee/customer data.

## Phase 2 controls and operational limits

Access JWTs use explicit HS256, issuer, audience, typ=JWT, required claims, maximum age and expiry. Each request rechecks current employee, authVersion, active session and active role grants. Permission snapshots in JWTs are not trusted. Refresh secrets are random 256-bit values stored only as SHA-256 hashes. Transactions serialize employee auth mutations and rotate a token once. Replay commits revocation of the entire token family before returning 401. Password reset/change invalidates all outstanding credentials and sessions.

A database-backed HMAC-keyed account throttle limits login to ten attempts and recovery to three attempts in a 15-minute window starting at the first attempt. It works across processes and resets expired rows without waiting for TTL deletion. The separate HTTP authentication limiter allows 30 requests/15 minutes/IP per process; ingress/shared limits remain required for horizontal deployment. Argon2 operations share a process-wide two-job pool with a maximum queue of sixteen to bound memory pressure; saturation returns AUTH_BUSY/429.

Reset/invitation records store only token hashes. An independent AES-256-GCM key encrypts delivery tokens using authenticated context; the SMTP worker decrypts only eligible jobs and deletes ciphertext after success/invalidation. SMTP requires TLS certificate verification. Delivery failures store retry state rather than provider errors that might expose recipient content. Reset responses are generic; no live SMTP messages are sent by tests. Recovery timing is not a cryptographic account-existence guarantee, so provider operations remain asynchronous and rate-limited.

Identity writes and their audit insert share transactions. Mongoose audit hooks reject update/delete/bulkWrite; production MongoDB runtime privileges must also deny raw audit updates/deletes. Permission delegation requires the exact actor-held capability; sensitive/ALL grants require permissions:delegate_sensitive. System roles cannot be deactivated/deleted; MD core administration grants cannot be removed. Phase 3 exposes employee deactivation/assignment with live source/destination, role-policy and last-administrator checks.

Use current patched Node/runtime/container versions and least-privilege operational credentials. Bootstrap/seed/index/delivery scripts run only in restricted environments. Store signing/encryption/SMTP secrets in a secret manager; do not log configuration. SMTP delivery, production MongoDB privilege enforcement and Docker image execution need real environment validation before rollout.

## Phase 3 organization controls

Employee/branch/location writes acquire a transaction-wide organization fence shared with role/policy administration, then reload the actor and live session. Expected revisions prevent lost updates. Manager-chain root, cycle and depth checks run under that fence, including active ancestor and descendant compatibility. Simultaneous reciprocal manager changes cannot both commit. Role/branch/status/manager mutations invalidate affected access sessions; descendant scopes are freshly queried on their next request.

Approved role templates bind creator and target revisions; changing either invalidates future creation/reassignment until reviewed. Sensitive and company-wide templates require explicit sensitive delegation. Ordinary branch visibility cannot be used to edit a peer manager or administrator. Assignment/status DTOs reject arbitrary actor IDs, hashes, grants and unrelated fields.

Contact changes and deactivation invalidate outstanding reset/invitation records and expire queued deliveries so old email links cannot regain access. Pending employees get new invitations after contact change/reactivation. Head transfer/deactivation or head-role capability removal requires explicit reassignment. Last-active-administrator protection uses effective core grants across active users/roles; the bootstrap root's placement/role stays protected.

Location chains are active and consistent; parent/code updates cannot silently reparent existing branches. Referenced masters and occupied branches cannot deactivate. No hard employee/branch deletion is implemented. Operational reference seeding requires vetted input, strict bounded JSON validation and atomic audit; it never executes or downloads user-supplied code.

Last-administrator availability requires an active employee with completed password setup and an active role containing the core administrator grants. Pending invitations do not satisfy this safeguard.

## Phase 4 evidence controls

Attendance writes reload the current session/role under the same organization transaction fence. Actor/branch/server timestamps are server-controlled; unique daily/open indexes and atomic expected revisions protect check-in/out. File attachment validates owner, matching purpose, confirmed freshness and unconsumed state in that transaction. Audit failure rolls back both attachment and attendance. Corrections preserve raw evidence, reset review, require another scoped actor and append before/after times/reason/revision.

Signed S3 POSTs bind generated keys, exact size, MIME, SHA-256 and AES256 encryption; metadata/signature checks pin an immutable non-null VersionId. All bucket public-access blocks, encryption and versioning are checked at storage boundaries. Downloads require parent attendance scope, pin that version and expire in 60 seconds; generic file downloads also enforce SELF/ALL file ownership. Existing signed capabilities cannot be instantly revoked. Logs redact photo locations, keys, signed URL/form fields and checksums in addition to existing credentials.

Camera/GPS/capture timestamps do not establish physical presence or liveness. Suspicious evidence is flagged for human review; no anti-spoof guarantee, full image decoder or malware scanner is claimed. Only supported image signatures are accepted and downloads use attachment disposition. Cleanup marks expired unattached files DELETING before storage deletion; no TTL removes retry metadata and attached evidence has no automatic deletion policy. See PHASE4.md for exact limits and deployment validation requirements.

## Phase 5 commercial controls

CSV requests use safe basenames, server-generated keys, exact-size/type/checksum/encryption POST policies and immutable version confirmation. Bounded streaming UTF-8 parsing rejects binary/NUL, malformed quotes, oversized files/rows/columns/cells and header mismatches before publishing a preview. Joi row validation, normalized E.164 phones and parent-qualified active location references precede staging. No formula is evaluated; export cells are quoted and spreadsheet-sensitive prefixes neutralized. Unexpected parser/provider exception contents are replaced by safe codes.

Scope predicates are applied before contact lists/counts, source writes and exports. Live job authorization includes creator/source hierarchy plus branch and destination on every batch, and cannot be bypassed by stale queued session/role snapshots. Assignment recipients require explicit receive capabilities and matching read authority. Unique dedupe keys, source-customer lead keys, idempotency keys and expected revisions defend races. Conversion/assignment/status changes and customer commit batches require atomic audit/history; failure rolls back the batch. Raw contact values and phone-bearing dedupe keys are excluded from audit metadata/logs.

DuplicateScope COMPANY can report a generic duplicate result for a submitted phone across branches; it exposes no conflicting IDs/names or other contact details. It is an explicit administrator policy chosen before data exists, not an implicit cross-branch read grant. Scope/source/recipient revocation can stop an import after some previously authorized batches commit; status/counts retain that progress for an explicit safe resume. Histories and workflow versions require insert-only database privileges in addition to ODM hooks. Source CSVs, staging, backups and exports contain customer PII and need approved operational retention.

Export requests are owner-bound, filtered at generation/publication, limited to 5000 rows/10 MiB and reauthorized for every included lead at download. Storage metadata exists before writes; orphan cleanup retains failed retry metadata. Signed links expire after 60 seconds but cannot be instantly revoked once issued. Staged row data expires after 30 days; job lifetimes independently prevent stale confirmation/download. Source/attached file deletion is not automated without a reviewed retention policy. Calls, visits, target verification and business dashboards remain later phases; a lead status alone is not verified physical/call evidence.

## Phase 6 evidence and reviews

Call/visit DTOs reject employee attribution, duration, storage metadata and extra fields. Durable per-report idempotency plus transaction serialization prevents duplicate retries; overlapping calls and stale revisions fail. Writes reauthorize current actors and assignments, including photo confirmation and completion. Invalid photo sets roll back all attachments. GPS/phone logs are untrusted evidence; stale capture/accuracy flags persist, and all records begin PENDING. No self approval is allowed. Submitted/approved totals remain separate. Private visit files use the Phase 4 immutable-version adapter and exact size/type/checksum/signature checks. Parent report scope controls 60-second download capabilities. No customer/GPS/discussion text is copied into audit metadata. Enforce insert/read-only DB permissions for report_history, as for existing immutable histories. See PHASE6.md for limits, retention and future provider verification.

## Phase 7 targets and verified evidence

Clients cannot set actuals, percentages, target branch/assigner, milestone attribution/times/value or source approval. Count goals are whole, monetary goals exact decimals, periods canonical and bounded. Transaction fences plus overlap/revision guards prevent concurrent duplicate assignments and stale edits. Immutable target/review histories and audits commit with writes; audit failure rolls back source lead events/evidence as well. Only approved original report IDs and deduplicated first lead milestones count. Reopening and reassignment cannot create new conversion credit or replace frozen value. Legacy missing/invalid frozen values cannot be approved. Independent milestone review excludes performer and beneficiary; withdrawal removes actuals on the next snapshot. Scope filters precede counts/sums; summaries are bounded to 500 definitions and reports paginate. No PII/review discussion or financial values are copied to audit metadata. See PHASE7.md for explicit historical snapshot authorization and operational limits.

## Phase 8 aggregate and export controls

Dashboard permissions never substitute for source permissions: each source intersects both before counts/groups, and exported sources also intersect export scope. Labels, role/manager/search and branch-geography dimensions are resolved through scoped records. Unavailable financial/source data is marked unavailable/null rather than invented zero. Employee/branch/global ranks are ordered before page slicing. Exact money remains Decimal128/BigInt strings. Raw customer contacts, GPS, photographs, notes and provider metadata do not appear in dashboard recent activities or metric exports.

Read calculations and export publication use fresh authorization/security fences and a coherent DB snapshot. Exports persist cleanup metadata before S3 writes, bind immutable encrypted/checksummed versions, and re-evaluate all dashboard/source/export access at generation/publication/download. Same-asOf CSV fingerprints reject stale or newly unauthorized aggregate files. CSV formula escaping is reused. File capabilities last 60 seconds; job lifetime/leases/retries and record/byte/range bounds are explicit. Calendar revisions/audits and eligible employee/source intersections prevent naive absence subtraction; absence remains provisional, and historical employment eligibility is unavailable. See PHASE8.md for limits and production-validation boundaries.
