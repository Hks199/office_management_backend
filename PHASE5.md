# Phase 5: customers, streaming CSV imports and leads

Implemented in API version 0.5.0 under `/api/v1`, after explicit user approval. Phase 6 reporting remains pending. GUIDE.md is unchanged. All routes require a live bearer session; writes refresh permissions/session state under the shared organization transaction fence and append required audit in the same transaction. The OpenAPI document includes the exact runtime DTOs.

## Upgrade and operations

1. Install the locked dependencies with `npm ci`. MongoDB must be a replica set.
2. Run `npm run db:indexes:commercial` with the operational migration identity. It creates identity/organization/attendance prerequisites and all commercial collections/indexes, synchronizes controlled permission definitions, and inserts missing duplicate settings and the immutable default workflow version. Existing customer data, custom grants, configured settings and workflow versions are preserved. Do not run old and new application versions concurrently during this migration.
3. Review assignment capability changes. Fresh bootstrap seeds `customers:receive_assignment SELF` for TC and `leads:receive_assignment SELF` for SEX. Existing role grants are preserved by index/seed commands. For an existing installation, the separate restricted command `npm run enable:commercial-capabilities` adds only these missing default capabilities and both SELF capabilities to the initialized bootstrap MD's system role for delegation. It requires an active bootstrap administrator with completed password setup, serializes with administration, audits each changed role and increments its revision. It does not reapprove creation policies. Review/reapprove affected policies through the existing policy API before creating more employees. Custom roles receive capabilities only through reviewed role administration.
4. Configure vetted active location masters and branches. Create real PAYMENT_MODE, PANEL_BRAND, PANEL_TECHNOLOGY and LEAD_SOURCE values through `/reference-values`; no production brands, technologies or payment modes are invented. Historical reference codes remain on leads after reference deactivation, while new/changed references must be active.
5. Configure `AWS_REGION` and `S3_BUCKET` together and use workload IAM roles. The existing private bucket must retain versioning, encryption and all public-access blocks. Review the expanded `infra/private-photos.yaml`: exact-origin POST/GET/HEAD CORS and separate runtime/cleanup permissions for `sunvika/attendance/*`, `sunvika/imports/*`, and `sunvika/exports/*`. No AWS resources or production records were provisioned during implementation.
6. Schedule `npm run jobs:commercial` at least every minute. It processes at most five import and five export attempts per invocation and needs the same database and private storage configuration as the API. Runtime image commands are `node dist/scripts/commercial-indexes.js`, `node dist/scripts/enable-commercial-capabilities.js`, and `node dist/scripts/process-commercial-jobs.js`. No Redis service is required; MongoDB stores durable job states and leases.
7. Continue scheduling `cleanup:orphan-photos` with the separate cleanup IAM role. It now cleans expired unattached CSV/export upload objects as well as photos, preserving retry metadata. Attached source CSVs and export versions have no automatic destructive retention. Export download authorization expires after 24 hours; storage retention is a separate approved operational policy. Staged row data has a 30-day TTL and import confirmation/resumption expires after seven days.

Both API and worker use bounded operations. Monitor QUEUED/FAILED age, expired leases, row counts, missing storage objects, orphan cleanup failures and organization-fence contention. The global fence favors correctness; load testing and finer-grained locking are Phase 9 work. Workers must finish/drain before schema migrations. Protect database backups and source CSVs as customer PII. Runtime database privileges should allow required commercial CRUD but only inserts/reads on `activity_logs`, `lead_assignments`, `lead_status_events`, and `lead_workflows`; internal setup requires separate privileges.

## CSV workflow

POST `/csv-imports/upload-intents` with `{filename,size,checksumSHA256}`. Filenames must be safe basename `.csv` values, size 1 byte–20 MiB, checksum the standard base64 SHA-256 of raw bytes. It requires imports:create, leads:import and files:upload. At most 20 pending/ready file intents per employee across purposes. Submit all returned signed POST form fields to S3 and append the file last. The policy binds exact size, content type text/csv, checksum, encryption and server-generated key; it expires in five minutes.

POST `/csv-imports/files/:id/confirm` as owner before expiry. HEAD verifies declared size/type/checksum/encryption and a non-null immutable version ID. Text formats have no reliable image-style magic signature: full UTF-8 and CSV structure validation happens in the background before a preview becomes visible or any customer is written. There is no executable spreadsheet processing or malware/liveness claim. Confirmation does not mean rows are valid.

POST `/csv-imports` with `{fileId,branchId,columnMapping?}` before intent expiry. File attachment and queued job/audit commit atomically. Files are owner-bound, purpose-bound, fresh and once-only. Import branch authority is required independently for both imports:create and leads:import. ALL can import anywhere active; BRANCH/SELF use the actor branch; DIRECT_REPORTS/REPORTING_SUBTREE use branches currently occupied by those visible employees. An unrelated branch cannot be supplied through the body.

Default mapping is:

| DTO field | CSV header |
|---|---|
| customerName | Customer Name |
| mobileNumber | Mobile Number |
| alternateNumber | Alternate Number |
| state | State |
| district | District |
| block | Block/Tehsil |
| siteAddress | Site Address |
| remarks | Remarks |

Custom mappings accept only those eight keys, distinct bounded header names, and require customerName/mobileNumber/state/district/siteAddress. Omit optional mappings when the CSV omits those headers. Headers must be unique and contain every mapped column. UTF-8 BOM and quoted commas/newlines/escaped quotes are supported. Invalid UTF-8, NUL bytes, malformed quoting or inconsistent column counts fail the entire preview; no partial preview is published. Limits are 50,000 customer rows, 16 columns, 2,000 characters per cell and 16,384-character parser record buffers. Parsing uses streaming backpressure and writes at most 50 staged rows in a transaction; it never loads the complete CSV into memory. See the parser's [streaming iterator](https://csv.js.org/parse/api/async_iterator/) and [limit options](https://csv.js.org/parse/options/) documentation.

SDK metadata requests have explicit failing timeouts. CSV body reads enforce a 30-second upstream wait deadline; time spent processing buffered rows or waiting on database backpressure is excluded.

Each row undergoes Joi validation, phone normalization and active location resolution. Ten Indian digits normalize to +91; explicit international E.164 numbers are accepted, with spaces, hyphens and parentheses removed. State/district/block may be vetted codes or case-insensitive exact names, resolved within the correct parent; unknown, inactive or ambiguous references reject the row. A bounded 1,000-entry location cache accelerates preview; commit revalidates active chains. Rejected rows return safe `rowErrors` codes, not raw parser/provider errors or another customer's data.

GET `/csv-imports`, `/:id`, and `/:id/rows` expose state, counts and paginated complete previews. Row filters are VALID/REJECTED/DUPLICATE/IMPORTED. Job list filters include branchId/status/page/limit/sortOrder. Lease IDs and persisted session/principal data are never returned. Creators can access their own job metadata when they retain imports:read; scoped managers can see authorized creator/team/branch jobs. Row access additionally requires current branch eligibility. A source upload cannot confer authority to import into a different organizational scope.

POST `/csv-imports/:id/confirm` with `{revision,assignedTo}` queues the commit. This is an explicit choice of an active same-branch customer-calling recipient, not an assignment hidden in the upload. It requires imports:confirm, leads:import and customers:assign for the current branch/destination. Subtree managers cannot assign to same-branch peers outside their subtree. No customer is live before confirmation. Confirmed batches become visible as they commit; large imports are intentionally not one giant transaction. Total accepted/rejected/duplicate/imported counts and per-row statuses expose progress.

Default duplicate policy is `(branchId, normalized mobileNumber)`. `/commercial-settings` allows settings:manage ALL to select BRANCH or COMPANY before any customer data exists, with expected revision. Policy freezes once data exists; changing it later needs an explicit data migration. Preview snapshots policy; worker publication/commit rejects a changed policy. Within-file and existing duplicates are reported without revealing customer IDs/contact data from another branch. Commit rechecks the unique dedupe key and skips duplicates introduced after preview. Unique `(importId,importRow)` and atomic row/customer/history/count writes prevent retry duplication.

Jobs use two-minute renewable leases, bounded staging/commit batches and at most three automatic attempts for unexpected storage/job failures. A worker restart reclaims expired leases. Validation restarts its private staging set; commits resume only VALID rows. Authorization, invalid CSV, stale policy or expired preview failures stop immediately. Permission/session revocation, inactive/moved recipients, disabled branches and changed locations are rechecked during commit; they can stop a partially completed import without undoing already-authorized committed batches. For a confirmed FAILED job within its lifetime, POST confirm again with its latest revision and the same assignee to explicitly resume. Failed validation needs a corrected/new upload. Failure responses store safe codes rather than arbitrary exception contents. Missing audit aborts that whole batch.

## Customers and conversion

GET `/customers` and `/:id` apply customers:read scope before filtering/count/pagination. Canonical `assignedTo` drives ASSIGNED/direct/subtree access, `createdBy` drives explicit SELF, and immutable branchId drives BRANCH. No implicit role-name bypass. Customer assignment recipients require `customers:receive_assignment SELF`, a read capability that can see assigned work, ACTIVE employment and the same branch. This permits reviewed custom calling roles without pretending every reports:create holder is a telecaller.

POST `/customers/assignments` accepts `{items:[{id,revision}],assignedTo,reason}` (1–100 unique IDs). It validates source visibility and each destination; all rows/history/audits commit or all roll back. Converted customers cannot be reassigned. GET `/:id/assignments` returns parent-authorized paginated history. PATCH `/:id/status` accepts `{revision,status,reason}` for AVAILABLE/INTERESTED/NOT_INTERESTED by the current caller or a scoped customers:assign manager. CONVERTED is not writable by this endpoint.

POST `/customers/:id/convert` accepts `{revision,requirements,proposedSalesExecutiveId?}` and a required `Idempotency-Key` of 16–100 alphanumeric/underscore/hyphen characters. Both customers:read and leads:create must authorize the source. Only interested, unconverted customers at their current revision are eligible. An optional same-branch eligible sales recommendation requires leads:propose_assignment; it creates a proposal, never silently assigns the lead. Conversion copies the validated source contact/location/branch, computes values and inserts lead/initial status event/proposal/idempotency record, links and increments the customer, and appends audit atomically.

Exact actor/key/body replay returns the same authorized lead; key reuse with a different request conflicts. Source-customer uniqueness plus retained customer link prevents repeated conversion even after 30-day idempotency metadata TTL cleanup. Different-key repeated conversion conflicts. TC's explicit leads:read SELF keeps their originated lead visible after assignment; salesExecutiveId is attribution only. An unassigned conversion lead requires creator SELF, BRANCH or ALL read access to retrieve later. Pure assignee-subtree grants do not implicitly expose unassigned leads; an appropriately branch/global-scoped manager handles proposals until assignment.

## Leads, assignments and workflows

POST `/leads` accepts contact, branch/location, configured references and requirements; optional assignedTo. Non-global creation needs a destination inside the action's branch/team/own-assignment scope. Assigning another employee at creation also requires leads:assign; self creation requires a same-branch eligible sales recipient. Global creators may leave a lead unassigned. Client actor IDs, status, workflowVersion, historical attribution and estimatedProjectValue are rejected. All new leads start NEW; assignment does not regress or silently change a progressed status.

Requirements are requiredCapacityKw/ratePerKw nonnegative decimal **strings**, at most eight integer and two fractional digits, plus active paymentMode/panelBrand/panelTechnology/leadSource reference codes, optional nextFollowUpAt. Quantities and rates use hundredths internally with BigInt; value is capacity × rate rounded half-up to INR paise and persisted as Decimal128. For example 5.00 kW × 55000.00 INR/kW = 275000.00 INR. Numeric JSON amounts, scientific notation, negative/overprecision values and supplied computed values are rejected. Responses serialize all monetary/quantity Decimal128 values as strings.

PATCH `/leads/:id` requires revision and editable contact/requirements fields; branch, assignee and status have separate contracts. Location chains and changed references are validated and value is recomputed. Terminal leads must reopen before profile/price changes. Assignment POST `/:id/assignments` takes `{revision,assignedTo,reason}` and requires old-record scope and prospective destination, an ACTIVE same-branch `leads:receive_assignment SELF` recipient with assigned-read capability, and immutable history/audit. Canonical assignedTo is the only assignment authorization field. Initial salesExecutiveId remains historical attribution on reassignment. Expected revisions make simultaneous assignments produce one success and a conflict.

POST `/:id/assignment-proposals` uses `{revision,assignedTo,reason}`; GET the same path lists parent-authorized proposals. A creator/current assignee can recommend an eligible same-branch recipient when explicitly granted proposal authority; manager proposals must also satisfy destination scope. One unresolved pending proposal per lead. PATCH `/lead-assignment-proposals/:id` with `{status:APPROVED|REJECTED,reason}` requires leads:assign and current source visibility. Approval rechecks seven-day expiry, lead revision, active recipient and destination and atomically records the assignment/review/audit. Reject stale/expired proposals before replacing them. An authority that could assign directly may approve its own recommendation; a proposer without assignment permission cannot approve.

PATCH `/:id/status` accepts `{revision,status,reason}` and validates against the lead's pinned workflow version. Default edges are NEW→ASSIGNED/CONTACTED, ASSIGNED→CONTACTED, CONTACTED→INTERESTED/NOT_INTERESTED, INTERESTED→QUALIFIED→SITE_VISIT_SCHEDULED→SITE_VISITED→QUOTATION_SENT, QUOTATION_SENT→NEGOTIATION/CONVERTED, NEGOTIATION→CONVERTED/LOST. Nonterminal working stages may go ON_HOLD or LOST with reason. Hold resumes only the saved prior stage. CONVERTED/LOST/NOT_INTERESTED reopen only to CONTACTED with scoped leads:reopen plus leads:update and reason. Status/assignment histories are append-only and parent-authorized. Conversion status events freeze that event's project value; they do not yet claim verified calling/site/installation activity or count target achievements.

GET `/lead-workflows` returns the latest version; POST creates a new immutable version with `{expectedVersion,transitions:[{from,to}]}` under settings:manage ALL. No self edges, arbitrary executable rules, terminal outgoing edges or uncontrolled hold resumes. Existing leads retain their version; changes govern new leads only. No workflow migration of existing leads is implicit.

Filters include branchId/assignedTo/createdBy, stateId/districtId/blockId, valid resource status, literal name/phone prefix search, half-open created-at and follow-up ranges, leadSource, page 1..10000, limit 1..100, asc/desc createdAt+ID sort. Date-only shared validators mean UTC midnight; use explicit-zone timestamps for business-time boundaries. Histories return bounded arrays using page/limit, while main lists include total metadata. Unauthorized individual IDs return generic 404. Transfers preserve branch/history and use current assignee hierarchy for visibility; dependent work is reassigned explicitly, never silently moved with the employee.

## Private exports and verification limits

POST `/leads/exports` with the validated lead filters (or `{}`) queues an owner-bound export requiring leads:export and leads:read. Worker preparation and publication intersect both live scopes. Exports reject over 5,000 leads or 10 MiB rather than silently truncating. Output quotes every CSV cell, escapes embedded quotes and prefixes spreadsheet-sensitive leading =,+,-,@ or tab/CR/newline (including whitespace/control prefixes). No formula is evaluated. PENDING file cleanup metadata is persisted before S3 write, so retries do not create untracked objects.

GET `/leads/exports/:id` reports state; GET `/:id/download` requires the creator's live grants, unexpired job and visibility of **every** included lead under both export/read scopes. Scope changes fail the old download rather than offering stale broader data. The URL pins the encrypted S3 version, forces attachment, requests no-store and expires in 60 seconds. It is a capability and can remain usable until its short expiry after subsequent revocation. Export data is a historical snapshot at generation time, not a live report.

Tests use isolated temporary MongoDB replica sets, injected commercial storage and mocked AWS SDK commands. They exercise bounded parsing, dedupe/commit races, eligibility and scope isolation, permission revocation, worker recovery, idempotent conversion, audit rollback, assignment races, proposal review, status transitions, exact decimal calculations, workflow versions, formula escaping, export reauthorization and explicit capability rollout. No production DB, real customer data, live AWS/S3/IAM/CORS deployment, SMTP or remote CI was used. Validate actual S3 permissions/browser upload/checksums and worker scheduling with your environment before rollout. Performance/load tests, formal retention/restore drills and verified calling/site reports remain later phases.
