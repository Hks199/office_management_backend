# Phase 4: attendance and private photo evidence

Implemented under `/api/v1` after user approval. Phase 5 customers/imports/leads are documented separately in PHASE5.md. See the generated OpenAPI document for request schemas and [API_DOCUMENTATION.md](API_DOCUMENTATION.md) for endpoint contracts.

## Setup

Use a MongoDB replica set and run `npm run db:indexes:attendance` with the operational migration identity before exposing these endpoints. This creates identity/organization prerequisites plus attendance/file indexes; it does not overwrite employee data, custom roles or approved policies. Existing branches without an attendance policy use the documented defaults. No AWS resources or production database were changed during development.

Configure `AWS_REGION` and `S3_BUCKET` together. They remain optional for unrelated APIs; photo upload fails closed with 503 when absent. Use the AWS default credential provider with workload IAM roles. Never put access keys in source or upload DTOs.

[infra/private-photos.yaml](infra/private-photos.yaml) is a reviewable CloudFormation template: private bucket, all public-access blocks, ownership enforced, AES256 encryption, versioning, TLS-only bucket policy and exact-origin POST CORS. Deploy it with your HTTPS frontend origin and attach its RuntimePolicy to your application role and CleanupPolicy to a separate cleanup role. Template deployment and real IAM/S3 validation are operational steps, not performed by the API. Existing buckets must meet these controls; every storage operation checks versioning, encryption and public access blocks. Bucket policies and IAM should restrict administrative changes to trusted operators.

Do not configure blanket current/noncurrent object lifecycle deletion: evidence references a specific version, which can become noncurrent if a still-valid upload URL is reused. Keep referenced versions until a retention policy is explicitly approved. This phase does not automatically delete attached evidence. Retention obligations and full disaster recovery validation require deployment-specific decisions.

## Photo workflow

1. Capture a current photo in the frontend. Calculate its raw-byte SHA-256 and encode the 32-byte digest as standard base64.
2. POST `/files/upload-intents` with `{purpose,filename,contentType,size,checksumSHA256}`. Purposes are `ATTENDANCE_CHECK_IN` or `ATTENDANCE_CHECK_OUT`. Only JPEG, PNG and WebP, 12 bytes–5 MiB, are supported. Safe filenames are checked for type/extension agreement; original names are not stored. Server-generated keys contain the authenticated employee ID and random UUID.
3. Submit multipart `FormData` directly to the returned S3 URL, including every returned `upload.fields` entry, then append the file last. The signed POST policy requires the exact declared size/type/checksum, encryption and key; expires in 300 seconds. S3 rejects bytes that fail its checksum ([AWS POST Object documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/RESTObjectPOST.html)). Do not send a JSON body to S3.
4. POST `/files/:id/confirm` before expiry. The server checks ownership, pending state and expiry, then HEAD size, MIME, checksum, encryption and a non-null immutable VersionId. A GET of bytes 0–31 from that exact version validates the file signature. Confirmation is atomic and once-only. A signature check does not fully decode images or provide malware/liveness verification.
5. Submit the file ID with matching-purpose attendance evidence before the five-minute intent expiry. Attachment, attendance state and audit commit together; files cannot be reused, attached by someone else or attached with another purpose. At most 20 unattached pending/ready intents per employee prevents unbounded issuance.
6. GET `/attendance/:id/photos/check-in` or `/check-out` for authorized evidence review. Access follows the parent `attendance:read` scope. GET `/files/:id/download` additionally enforces `files:read SELF/ALL` ownership scope and parent attendance scope. Neither returns arbitrary object references. URLs pin the confirmed version, force attachment, request no-store caching and expire after 60 seconds. As bearer capabilities, already-issued URLs can remain usable until expiry after a permission change.

The API and logs never return stored object keys, version IDs or checksums in file metadata responses. Upload URLs/form fields and short-lived download URLs are capabilities and necessarily reveal their S3 destination to the authorized client; do not log or share them. MongoDB stores references, never image binaries.

`npm run cleanup:orphan-photos` processes at most 100 files whose upload expiry is over 24 hours old and which are unattached. It atomically marks DELETING before S3 work, preventing concurrent attachment; removes all exact-key versions and delete markers in bounded pages, then records DELETED. A failed deletion keeps metadata for retry. Run hourly with restricted operational credentials. Attached photos and recent intents are excluded. Metadata has no TTL deletion. Cleanup must run for expired pending/ready intents to stop counting against the upload cap.

## Attendance evidence and business rules

Check-in/out accept exactly `{photoFileId,capturedAt,location:{latitude,longitude,accuracyMeters?}}`. Actor and branch come from the live authenticated user, not the body. Timestamps require a valid explicitly-zoned ISO date-time. Latitude is −90..90, longitude −180..180, optional accuracy 0..100000 meters. Server UTC timestamps are authoritative; client timestamps are evidence only. The business date is calculated in Asia/Kolkata.

Unique employee/date and unique employee/open indexes plus transaction serialization prevent duplicate check-ins and double checkouts. One check-in per business date; no multiple shifts. Checkout closes the employee's open record within 24 hours, including across Kolkata midnight, and keeps its original business date and branch attribution. An older unresolved open record requires an authorized correction before another check-in. No general overnight shift schedule or payroll policy is assumed.

Branch `attendancePolicy` is a complete replacement object on branch create/update. Updating it requires `branches:update ALL`, expected branch revision and the existing transactional audit. Defaults: no schedule/geofence, grace 0 minutes, GPS accuracy threshold 100 meters, capture age 300 seconds. An optional schedule requires both `startMinute` and `endMinute` as Kolkata minutes since midnight with end > start; overnight schedule definitions are rejected. Grace 0..120 minutes applies to arrival. A geofence specifies latitude, longitude and radius 10..100000 meters. Accuracy threshold is configurable 1..10000; capture age 30..900 seconds.

The complete policy is snapshotted at check-in and used through checkout/corrections even if the branch later changes. Late arrival means after scheduled start plus grace; early exit means before scheduled end. Without configured hours both flags are false. Evidence flags accumulate: `CAPTURE_TIME_SKEW` for capture older than the policy or over 60 seconds in the future, `ACCURACY_MISSING`, `LOW_GPS_ACCURACY`, `OUTSIDE_GEOFENCE` using great-circle distance. Flags queue evidence for human review, rather than preventing legitimate field workers from recording attendance. Every submission starts PENDING, including unflagged evidence.

Browser GPS, client timestamps and photos are evidence, not proof against spoofing, replay of old imagery, camera injection or location tampering. The server cannot establish a photograph's actual capture time from these fields. Device attestation, image liveness/decoding, antivirus and third-party verification are outside this phase.

## Reviews, corrections, history and summaries

GET `/attendance/me/status` requires `attendance:create` and returns only the authenticated employee's valid next action (`check-in`, `check-out`, or null) plus a user-facing message. It reads current organization authorization in a transaction, checks open records without a month filter, and checks today's Kolkata business date. Completed daily attendance and open attendance older than 24 hours have no available action. The frontend uses this endpoint before requesting GPS, then opens the camera only after location succeeds. The mark endpoints remain authoritative if attendance changes after the status read.

History, employee/branch calendars and summaries intersect permission scopes with validated filters before returning records or aggregating. SELF, DIRECT_REPORTS, REPORTING_SUBTREE, BRANCH and ALL retain their existing meanings. Historical branchId is preserved on transfer; current reporting hierarchy controls subtree visibility, consistent with the existing organization contract. Unauthorized employee/branch list filters produce empty lists without exposing existence. All responses use Cache-Control no-store.

History is limited to one requested month (YYYY-MM, years 2000–2099; default current Kolkata month), page 1..10000, limit 1..100, stable date/ID sort. Optional employeeId, branchId, status, reviewStatus, lateArrival and earlyExit filters are intersected. `/me` always adds the actor. Summaries return daily records/completed/pending/rejected/late/early counts and fractional workedMinutes for completed effective time intervals whose review is not REJECTED. Pagination is ignored for summaries; filters still apply. Only dates with matching records are returned. Missing calendar dates mean no recorded attendance, not an inferred absence; holidays, leave, expected staffing, breaks and payroll totals need future policies. Pending evidence is provisional and included in minutes; consumers must filter APPROVED when they require approved totals.

PATCH `/attendance/:id/review` requires scoped `attendance:review`, `{revision,reviewStatus,reason}`, and another employee as reviewer. It supports APPROVED/REJECTED/PENDING. Checkout invalidates an earlier review and requires a fresh one. POST `/attendance/:id/corrections` requires scoped `attendance:correct` and `{revision,effectiveCheckInAt,effectiveCheckOutAt,reason}`. No self corrections. Effective check-in must keep the business date, timestamps cannot be future or reversed, duration <=24h, and completed records cannot reopen. An administrator may close a missed checkout without inventing a photo or overwriting raw evidence.

Corrections preserve original check-in/out timestamps, GPS, capture timestamps and photo IDs. They alter only effective times, derived schedule flags/status and review state; mark corrected and return to PENDING. Append-only audit includes before/after effective times, actor, reason and revision in the same transaction. Missing audit insertion aborts the business change and photo attachment. There is no attendance hard delete or client-supplied attendance creation for another employee.

## Verification boundary

Replica-set integration tests exercise routes, state races, scope isolation, upload ownership/lifecycle, evidence flags, branch-policy validation, reviews, corrections and audit rollback. Injected photo storage prevents AWS calls. AWS adapter tests inspect exact SDK commands, POST conditions, version-pinned range/download requests, security checks, mismatch rejection and version cleanup. Real S3/IAM/CORS, frontend camera capture and CloudFormation deployment must be validated in the target environment.
